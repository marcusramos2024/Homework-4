⏺ I read docs/plans/league-setup.md, US-1 in the PRD, and the code in
  src/lib/league. I didn't change any files, and I didn't read time.test.ts or
  testData.ts.

  The code follows the plan closely. Decisions 1–6 are implemented as written.
  The commit order matches the plan, and every US-1 criterion except the 403 is
  covered. The differences are below.

  Where the code differs from the plan

  1. INVALID_INPUT is not in the plan. The plan says "SLOT_OUTSIDE_SEASON,
     SLOT_OVERLAP, and so on". The code adds an INVALID_INPUT code for Zod
     failures (types.ts:41), and the test table doesn't mention it.
  2. Decision 1 only holds after the schema passes. validateLeague.ts:12-20
     returns early on any schema error. One bad start like "7pm" hides every
     overlap and out-of-season error in the same submission. The plan's example
     of a coordinator entering 40 slots and seeing all the bad ones at once only
     works once the formats are clean.
  3. Two unplanned rules were added:
     - Names are capped at 100 characters, and sport reuses the same rule
       (schema.ts:5).
     - A division's teams defaults to [] (schema.ts:30), and a test covers it.
  4. Two tests are weaker than the plan's table says.
     - The plan lists "schema rejects a missing name". The test only covers a
       blank name ("   "), not an absent field.
     - The plan lists "a bad date format". The test uses 2027-02-30, which is a
       well-formed but non-existent date, not something like 01/18/2027.
  5. The helpers differ from the plan. time.ts also exports isTime and
     MINUTES_PER_DAY, and testData.ts is a new file. The plan lists only
     isRealDate() and toMinutes() in time.ts.

  What the plan missed

  1. Season end before start produces noisy output. With seasonEnd < 
     seasonStart, every slot is also outside the season. The code reports
     SEASON_END_BEFORE_START plus a SLOT_OUTSIDE_SEASON for each slot. The test
     avoids this by setting venues = [] (validateLeague.test.ts:29). The plan
     doesn't say which behavior is intended.
  2. IDs aren't checked for uniqueness. Duplicate slot, venue, team or division
     IDs pass. Errors point at slots by ID, so two slots with the same ID make
     SLOT_OVERLAP and SLOT_OUTSIDE_SEASON ambiguous. That works against the
     plan's reason for typed errors, which is that the UI can highlight the
     exact slot.
  3. An empty league is valid. venues has no minimum, and a venue can have zero
     slots. The PRD says "a venue has … a list of time slots" and doesn't
     require any. The plan's goal is a league "the scheduler can trust", and a
     league with no venues or slots can't produce a schedule. The plan should
     state whether this is intended.
  4. The league has no time zone field. CLAUDE.md says dates and times are in
     the league's local time zone. League doesn't record which zone. US-3's
     "late slot starts at or after 21:00" and the UTC-in-the-DB rule will both
     need it. This isn't a US-1 criterion, but it's cheapest to add now.
  5. No settings for later stories. US-2 has a per-league blackout limit
     (default 3) and US-7 has a configurable bracket size K. Neither has a field
     yet. The plan could note that they're deferred.
  6. Unknown fields are dropped silently. Zod's default object schema removes
     unrecognised keys. That's safe, but the plan doesn't say whether unknown
     keys should be rejected.
  7. The 403 follow-up has no pointer. The plan says it's "logged as a
     follow-up", but it doesn't say where. CLAUDE.md's definition of done needs
     an integration test with an allowed and a denied role, so it's worth
     linking to an issue.

  Decision 4 (slots can't cross midnight) is sound. It's also what makes the
  same-date-only overlap check in findOverlaps correct.

  I'd prioritise items 1–3 and 7 of the missed list. They're small and affect
  whether the validated League can be trusted.
